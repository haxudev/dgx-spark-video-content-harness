## 二、项目目标

### 2.1 总目标

用一条**全自动、可断点续跑、可离线降级**的流水线，把「数据分析结果」直接转化为「可发布的短视频内容」，让**每场**的足球赛前观察内容具备**规模化、稳定、合规**的生产能力，做到「数据一进、成片就出」。

### 2.2 分解目标

1. **结构无关的输入适配**
   报告解析层只识别通用 Block 类型（KPI 卡 / 表格 / 卡组 / 告示框 / 列表 / 图表提示…），新版式不识别时降级为 `unknown` 而非崩溃；数字必须可回溯到原始数据块，杜绝「模型幻觉出来的数字」上屏或入口播。
2. **音频即时间基准的确定性渲染**
   先做 TTS 拿到精确时长，再据此构建视频时间轴（hyperframes 确定性渲染 + ffprobe 校验音画同步），保证「口播说到哪、画面就到哪」，并可用 `|Δduration| ≤ 0.5s` 硬校验。
3. **内容规则与工程解耦**
   写作规则、术语表、合规话术、拒绝词全部由 `config/*.yaml` 管控，业务方改内容不动 TypeScript。
4. **合规优先，默认「去投注化」**
   全程只做「赛前概率观察 / 体育数据讨论」，公开成片中不得出现彩票、投注、下注、购买、赔率、庄家、推荐、资金安排、收益承诺等引导性表达；开场收场固定念免责声明；数字「画面上给、口播里不报」。
5. **Agent-first、CLI 优先、无 MCP 依赖**
   稳定接口是 `harness` 命令行，任意极简 coding-agent 或 Microsoft Agent Framework 托管 agent 都能直接驱动，不引入 MCP 或重依赖。

### 2.3 成功判据（可度量）

- 输出：1080×1920、H.264 + AAC，时长落在目标区间（单场 `[145, 195]s`）。
- `compliance.json` 审计：开场命中 `simulated/仅供研究` 类标注，收场命中「不构成建议 / 仅限合法体彩·体育讨论 / 未成年人禁止参与」等固定句。
- 端到端冷启动 ≈ 15 分钟（RENDER 约占 7 分钟），热运行（TTS 命中缓存）≈ 5 分钟。
- 全链路可离线跑通：无 LLM 时 WRITE 回退确定性模板，无 TTS 时回退占位音频，无 Chrome 时跳过 RENDER——保证 CI/测试不依赖云凭据。

## 三、项目背景

### 3.1 行业与场景背景

足球赛事分析领域已经积累了大量结构化数据（胜平负概率、总进球分布、比分热力、半全场走势、爆冷指数、风向标概率漂移等），但这些数据的**最后一公里**——把冷冰冰的表格变成「人愿意看、看得懂、可以每天追」的短视频内容——长期依赖人工：写稿、配音、做图、剪辑、加合规角标，一场比赛动辄数小时，根本无法覆盖「每天几十场」的体量。

与此同时，短视频平台对**竖屏、口播、大字号、强节奏**的内容消费习惯已经定型；而涉彩合规红线又要求内容必须严格「去投注化」、只做数据与概率讨论。这就形成了一个明确的工程命题：

> **能不能让「一份分析报告」自动变成「一条合规的竖屏解说视频」？**

### 3.2 技术背景

本项目诞生的另一半背景，是团队手里握有一套**本地私有的 AI 基础设施 —— Nvidia DGX Spark**：

- **Nvidia DGX Spark = 一台本地推理网关**，以 OpenAI 兼容协议对外服务，托管着 **Qwen3.6-35B「思考型」大模型**（`http://Nvidia DGX Spark.haxu.home:8000/v1`），同时还统一网关了 **Qwen3-TTS 语音合成**（音色注册 / ICL 克隆）与 **LongCat-Video-Avatar 数字人**能力。
- 这台机器上「大脑（LLM）」「嗓子（TTS）」「脸（数字人）」共享同一批 GPU，谁用谁占显存——这既是成本优势（自有算力、可克隆专属音色、数据不出内网），也是本项目一系列独特工程设计（时间片让渡、缓存-only 消费、思考预算裁剪）的根本约束来源。

正是「**内容生产刚需**」与「**本地 Nvidia DGX Spark 私有算力**」两者叠加，催生了这条以 Nvidia DGX Spark Qwen3.6 为核心大脑、以合规为第一约束、以 agent 全自动驱动的短视频生产线。
